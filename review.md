## The verdict

This is a good project. Not "good for someone learning Swift" — actually good. You picked a real
problem, you picked the right two libraries for it, and the shape of the solution is correct. The
streaming export in particular is the thing most people get wrong on their first attempt, and you
got it right without being told.

What's holding it back is not Swift knowledge. It's that roughly 110 lines of `Export.run()` are
doing eight jobs at once, and a handful of habits from another language came along for the ride.
Those are cheap to fix and the lessons transfer.

The most serious finding in this review is not a Swift issue at all — it's that you're storing
database passwords in plaintext and passing them on the command line. Read the Security section
first.

## What it does well

Genuine strengths, not consolation prizes.

- **[High] You stream instead of buffering.** `Export.swift:170` — `let documents = collection.find()`
  followed by `for try await document in documents` means a 40GB collection exports in constant
  memory. The obvious first instinct is `let all = try await collection.find().drain()`, and it
  works beautifully right up until it OOMs on real data. You skipped that entire class of bug.
- **[High] It compiles clean under Swift 6 language mode, today.** I tested it. Zero warnings, zero
  errors. That is genuinely uncommon for a project written in Swift 5 mode, and it means your
  instincts about value types and shared state are already correct.
- **[Medium] `ShellRenderable` is the right *shape* of solution.** `extensions.swift:52` — a
  protocol with per-type conformances, instead of one giant `switch` over `Any`. The execution has
  a hole (see below), but you reached for polymorphism where most people reach for a type-switch.
- **[Medium] `defer { coordinator.close() }` immediately after `open()`.** `Export.swift:167-168`.
  Textbook. The stream closes on every exit path including thrown errors.
- **[Medium] The `quote(_:)` escaper is genuinely careful.** `extensions.swift:31-45` handles
  control characters below `0x20` via `\u%04x`, not just the obvious quote-and-backslash pair. That
  is the part people forget, and it is the part that corrupts files.

## Architecture

### Dependency sketch

```
Mport (root command)
  └─> ConfigureDefaults / RegisterConnection / Export / Import
        ├─> CLIConfig  (static read/write, hits ~/ directly)
        ├─> OutputFormat
        ├─> CLIError
        └─> MongoKitten + Foundation  (network + file I/O inline in run())
```

There are no wrong-direction arrows — nothing low-level reaches back up into the commands. That's
good, and it's largely because there's only one layer. The problem is the missing middle, not a
broken dependency.

### What it does poorly

- **[High] `Export.run()` is eight jobs in one function.** `Export.swift:30-142`, ~110 lines:
  default-path resolution, format resolution, connection selection, interactive prompting, network
  connection, database selection, collection selection, and dispatch. Every one of those is
  independently testable logic, and none of it can be tested, because it's all welded to a live
  Mongo connection and to `stdin`.
- **[High] There is no seam anywhere.** `CLIConfig.read()` (`CLIConfig.swift:22`) is a `static func`
  that reaches straight into `FileManager.default.homeDirectoryForCurrentUser`. There's no way to
  point it at a temp directory, which means there is no way to test config handling without
  clobbering your actual `~/.mport-config.json`. Same for the prompts: `readLine()` is called
  directly, so no test can drive them.
- **[Medium] `structs/` and `utils/` group by *what things are*, not *what they do*.** This is the
  folder equivalent of naming a variable `stringValue`. `utils/` currently holds an enum of error
  cases, an enum of output formats, and 125 lines of BSON-to-shell-JSON rendering logic. Those
  three have nothing to do with each other beyond "not a command."
- **[Medium] `extensions.swift` is a grab-bag hiding a real component.** 125 lines in a file named
  after a language feature. Inside it: an `OutputStream` convenience, a date formatter, a JSON
  string escaper, a `ShellRenderable` protocol, and nine conformances. The shell renderer is a
  *feature* of your tool — arguably the most interesting one — and it's filed under "misc."
- **[Low] No `Package.swift`.** This is an Xcode-only project, so it can't `swift build`, can't
  `swift package experimental-install`, and can't build in CI without a full Xcode. For a CLI tool
  that's backwards — SwiftPM is the natural home, and you'd get a test target for free.

### Proposed target structure

```
Sources/mport/
  Commands/
    Mport.swift                 # root command only
    ConfigureDefaults.swift
    RegisterConnection.swift
    Export.swift                # parses args, calls ExportService. ~40 lines.
    Import.swift
  Configuration/
    CLIConfig.swift             # gains an injectable directory URL
    MongoConnectionRecord.swift
    OutputFormat.swift
  Export/
    ExportService.swift         # the actual export logic, no ArgumentParser import
    ShellJSON.swift             # ShellRenderable + conformances, lifted out of extensions.swift
  Support/
    CLIError.swift              # + LocalizedError conformance
    Prompt.swift                # the interactive picker, behind a protocol
    OutputStream+Write.swift
Tests/mportTests/
Package.swift
```

- `Commands/` — argument declarations and nothing else. A command's job is to turn `argv` into a
  call; it should read like a summary.
- `Configuration/` — everything about persisted settings, named for its role, not its shape.
- `Export/` — the domain logic, with no `import ArgumentParser`. That import's absence is the test
  that proves the boundary is real.
- `Support/` — genuinely cross-cutting helpers. Keep it small; if it grows past ~4 files it has
  become another `utils/`.

### Migration order

Lowest risk first, each step leaving the project building:

1. **Add `Package.swift`** and move sources under `Sources/mport/`. Pure file movement, no logic
   changes, and it immediately unblocks a test target. Xcode opens SwiftPM packages natively, so
   you lose nothing.
2. **Lift `ShellRenderable` and friends out of `extensions.swift` into `Export/ShellJSON.swift`.**
   Cut and paste — no edits. Now the thing you'd most like to test lives somewhere findable.
3. **Give `CLIConfig` an injectable directory.** `init(directory: URL = .homeDirectory)` instead of
   reaching for the home directory inside each static method. One small change, and config handling
   becomes testable.
4. **Extract the prompt loop into `Prompt.swift` behind a protocol** with a real implementation and
   a scripted test implementation. This is what kills the "can't test anything interactive" problem.
5. **Extract `ExportService`**, moving everything from `Export.run()` except the `@Argument`
   declarations. Do this last — by now the first four steps have made it mostly mechanical.

## Line-level: `Export.swift`

### Outright wrong

- **[High] `Export.swift:86` — the same condition twice.**
  ```swift
  if connectionURI.isEmpty || connectionURI.isEmpty {
  ```
  The second operand was meant to be `validatedConnectionName`. Today it's harmless because both
  are set together, but it's a tripwire: the moment those two can diverge, this silently does the
  wrong thing. The compiler can't help you here — which is exactly why this pattern is worth
  noticing.

- **[High] `Export.swift:234` — piped or redirected stdin hangs forever.** `readLine()` returns
  `nil` at EOF, your `guard` treats `nil` as bad input, prints "Invalid input, please try again",
  and `continue`s — forever. I reproduced this in isolation: it spins indefinitely, printing
  endlessly, until killed. `mport export … < /dev/null`, or running under CI, or any pipeline, is
  an infinite loop today. `nil` from `readLine()` is not invalid input; it's "the user is gone,"
  and it needs its own branch that throws.

- **[High] Bad arguments silently become interactive prompts.** Three places: `Export.swift:79-84`
  (unknown `connectionName`), `Export.swift:111-115` (unknown `dbName`), and `Export.swift:60-64`
  (unrecognized `format`). In each, a typo'd value fails to match, the variable stays empty, and you
  fall through to a picker. So `mport export ~/out prodd mydb json` doesn't say "no connection named
  'prodd'" — it quietly asks you to pick one. Combined with the EOF bug above, a scripted typo
  becomes a hang. A CLI should be loud when given something it doesn't recognize.

- **[Medium] `Export.swift:152` — `default:` in a switch over your own enum.** `getPath(from:format:)`
  handles `.json`, `.bson`, `.mongoShellSyntax`, then `default: throw`. Add a `.csv` case tomorrow
  and this compiles perfectly and fails at runtime. Delete `default:`, handle `.pending` explicitly,
  and the compiler becomes the thing that reminds you. Same applies to the `if/else if/else` chain
  at `Export.swift:172-207`, which should be a `switch` for the same reason. **This is the single
  highest-leverage habit change in this review** — an exhaustive `switch` over your own enum turns
  a future runtime bug into a compile error, for free.

- **[Medium] `Export.swift:177` — ignored write result and a force-unwrapped base address.**
  `OutputStream.write` returns the byte count actually written, or `-1` on failure. You discard it.
  On a full disk you produce a truncated file and then print `exported '…'` as though it worked.
  Check the return value and throw on `-1`. The `baseAddress!` is also a force-unwrap that's only
  safe because `readableBytes > 0` in practice — `guard let` it.

### Design and idiom

- **[High] Every parameter is positional, which makes most of them unusable.** `Export.swift:15-28`
  declares four `@Argument`s. To specify `format` you must also supply `exportPath`,
  `connectionName`, and `dbName` in exactly that order. You cannot say "default path, but BSON
  please." These want to be `@Option(name: .shortAndLong)`:
  ```swift
  @Option(name: .shortAndLong, help: "Directory to export to")
  var path: String?

  @Option(name: .shortAndLong, help: "Format of exported files")
  var format: OutputFormat?
  ```
  Note `OutputFormat` directly rather than `String` — make it conform to `ExpressibleByArgument` and
  ArgumentParser validates the value *and* lists the valid ones in `--help` for you. Right now you
  hand-roll that with `OutputFormat(rawValue:)` and get a silent fallback instead of an error.

- **[Medium] `Export.swift:32-37` — all variables declared at the top.** Six `var`s before any work
  happens. That's a C/JavaScript habit, and Swift actively punishes it: `var connectionURI: String = ""`
  can't be `let`, can't be checked for exhaustive assignment, and forces `""` to mean "not set yet."
  Declare at point of use, prefer `let`, and let the compiler prove each value is assigned exactly
  once.

- **[Medium] `Export.swift:138` — `.filter { … }.first` should be `.first(where:)`.** `filter` walks
  the entire array and allocates a new one just to take element zero. But look closer and the whole
  lookup is unnecessary: you already have `selectedCollectionIndex` from the picker, so
  `availableCollections[selectedCollectionIndex]` is the answer. You converted to names, picked an
  index, then searched by name to get back the object you already had.

- **[Medium] `Export.swift:212-240` — `promptUserFromList` returns an `Int`.** Returning a bare index
  means every caller does `options[returnedIndex]` and every caller could get that wrong. Return the
  *element* instead and the off-by-one becomes impossible:
  ```swift
  func promptUser<T>(from options: [T], message: String, label: (T) -> String) throws -> T
  ```
- **[Low] `Export.swift:218-219` — a latent trap in the padding maths.**
  `String(repeating:count:)` traps on a negative count, and `padding - indexLabel.count` goes
  negative once the index label exceeds 8 characters — i.e. at option number 100,000. You will never
  have 100,000 collections, so this is not a bug you'll hit. It's here because the *pattern* is worth
  seeing: arithmetic feeding a `count:` parameter is a crash waiting for the right input. I confirmed
  it traps with `Fatal error: Negative count not allowed`. Use `.padding(toLength:)` or clamp with
  `max(0, …)`.

- **[Low] Small stuff.** `Export.swift:51` `config.connections.isEmpty == false` → `!config.connections.isEmpty`.
  `Export.swift:66` `exportFormat == OutputFormat.pending` → `.pending`. `Export.swift:57-59` re-tests
  `config.defaultFormat` with `if let` inside a branch that already proved it non-nil.
  `Export.swift:122` builds a path with string interpolation — use `URL.appending(component:)`, which
  handles trailing slashes correctly. `Export.swift:100` names a `MongoDatabase` `client`, then uses
  it only to reach `client.pool`.

## Line-level: `extensions.swift`

- **[High] The renderer silently corrupts BSON types it doesn't know about.** `extensions.swift:47-50`:
  ```swift
  fileprivate func render(value: Primitive, indent: Int) -> String {
      (value as? ShellRenderable)?.shellJSON(indent: indent)
          ?? quote(String(describing: value))
  }
  ```
  That `??` is a silent fallback to a *quoted string*. I checked BSON 8.2.2's actual read path
  (`Document+Mutations.swift`), and these `Primitive` types can come back from a real document and
  have no `ShellRenderable` conformance: **`Binary`, `Decimal128`, `Timestamp`, `RegularExpression`,
  `JavaScriptCode`, `JavaScriptCodeWithScope`, `MinKey`, `MaxKey`.**

  So a document containing binary data doesn't fail — it exports as a quoted debug description, which
  is neither valid shell syntax nor recoverable data. Silent wrong output is worse than a crash,
  because you won't find out until you try to restore. Make the fallback `throw` instead. If you can't
  render it faithfully, say so.

  (I also checked whether the missing `Int64` conformance mattered — it doesn't. BSON reads `.int64`
  back as `Int`, which you do cover.)

- **[Medium] Conforming stdlib types to your protocol pollutes the whole module.** `extensions.swift:74-102`
  adds `shellJSON()` to every `Int`, `String`, `Bool` and `Double` in the target. It compiles — you own
  the protocol, so this isn't the "retroactive conformance" warning — but now autocomplete on every
  integer in your codebase offers a MongoDB shell method. A single `enum ShellJSONRenderer` with a
  `static func render(_ value: Primitive) throws -> String` keeps the same logic, removes the
  `as? ShellRenderable` dance, and lets a `switch` tell you when BSON adds a type.

- **[Medium] `Double.infinity` and `.nan` emit invalid output.** `extensions.swift:86-90` returns
  `"\(self)"`, which produces `inf` and `nan` — valid in neither JSON nor mongo shell syntax. Mongo
  can genuinely store both. Handle them explicitly.

- **[Low] `extensions.swift:17` — same force-unwrapped `baseAddress!` as in `Export.swift`.** For an
  empty string, `Data(string.utf8)` is empty and `baseAddress` may legitimately be `nil`. `guard`
  on empty and return early.

- **[Low] `extensions.swift:56-60` — `shellJSON()` with no arguments is dead code.** The protocol
  extension providing the zero-argument overload is never called; every call site passes an explicit
  indent. Delete it.

## Concurrency & Swift 6 readiness

**Assumptions:** Swift 5 language mode, no explicit strict-concurrency setting,
`SWIFT_APPROACHABLE_CONCURRENCY = YES`, macOS 26.5.

### [Swift 6 compile error]

None. I verified this rather than guessing: a full rebuild with `-swift-version 6` reaching the
frontend produced **zero errors and zero warnings**.

**So flip the switch.** Set `SWIFT_VERSION = 6.0` in build settings today. It costs you nothing
right now, and it means the Import feature you're writing this afternoon gets checked properly
while it's 40 lines instead of 240. Migrations are cheap when the project is small and brutal when
it isn't — you are currently in the cheap window, with proof.

### [Latent race]

None found. Single-threaded command flow, no shared mutable state across tasks, no unstructured
`Task {}`, no continuations, no `@unchecked Sendable`. Value types throughout. This is a real
compliment — it's the direct result of the design choices praised above.

### [Style]

- **[Medium] `readLine()` blocks a cooperative thread pool thread.** `Export.swift:232-239` is a
  synchronous blocking read called from `async run()`. With MongoKitten's NIO event loops running
  alongside, you're occupying a cooperative thread while waiting on human typing speed. Today it's
  harmless — one command, one prompt at a time. It's worth understanding *why* it's a smell: the
  cooperative pool sizes itself to your core count, and blocking threads in it is exactly how async
  code deadlocks once there's any real concurrency. If you later do concurrent exports, this is the
  thing that bites.

- **[Medium] The Mongo connection pool is never closed.** `Export.swift:103` connects and nothing
  ever shuts it down. Process exit papers over it, but relying on that is a habit that fails the
  moment this logic moves somewhere long-lived. Add a `defer` that closes the pool, and while you're
  there check that `mport export` actually exits promptly rather than lingering on NIO threads.

- **[Low] `Import.swift:20` uses `static var configuration: CommandConfiguration { … }`** — a
  computed property, rebuilt on every access, where every other command uses `static let`. Match the
  others; `static let` is the idiom.

### Migration order

1. Set `SWIFT_VERSION = 6.0`. Verified to be a no-op today.
2. Add `SWIFT_STRICT_CONCURRENCY = complete` and confirm still clean.
3. Then, and only then, add the `defer` pool shutdown and the prompt extraction — with Swift 6 on,
   the compiler checks your new code as you write it.

## Security

This is the most serious finding in the review, and it isn't a Swift problem.

- **[High] Connection URIs are stored in plaintext at default file permissions.**
  `CLIConfig.swift:44-58` writes `~/.mport-config.json` via `Data.write(options: .atomic)`, which
  creates the file with your umask — typically `0644`, world-readable. A Mongo URI is
  `mongodb+srv://user:PASSWORD@cluster…`, so every database credential you've registered is sitting
  in a world-readable file in your home directory. Any process running as any user on that machine
  can read it.

  Minimum fix: write with `POSIXPermissions: 0o600` and verify with `ls -l`. Real fix: keep the
  non-secret parts in JSON and put the password in the Keychain.

- **[High] The URI is passed as a command-line argument.** `RegisterConnection.swift:21-22`. Two
  consequences people consistently underestimate: the password is written verbatim into
  `~/.zsh_history`, and it is visible in `ps` output to every other user on the machine while the
  command runs. Prompt for it instead with terminal echo disabled (`readpassphrase(3)`, or toggle
  `ECHO` off via `termios`), or read it from an environment variable.

Neither of these is exotic. They're the two mistakes essentially every credential-handling CLI makes
once, and they're much easier to fix now than after you've registered fifteen connections.

## Config robustness

- **[High] `CLIConfig.read()` destroys a valid config on any decode failure.** `CLIConfig.swift:28-39`
  catches *everything* and responds by overwriting the file with an empty config. That catch fires
  for a transient I/O error, a permissions problem, or — the one that will actually get you — a
  schema change. Add one non-optional property to `CLIConfig` and every existing user's saved
  connections are silently erased on next launch, with a message claiming the file was "malformed."

  Distinguish the cases: file-not-found is normal on first run and deserves no warning at all;
  a decode failure on a file that exists deserves a loud error and a `.backup` copy, never a silent
  overwrite. This is the classic `Codable` migration trap, and it is worth internalising now.

- **[Medium] `CLIConfig.write` refuses to write if the file doesn't exist.** `CLIConfig.swift:48-50`
  throws `.missingConfig` when the file is absent — but writing is precisely how you'd fix that. It
  only works because `read()` always runs first and creates the file, which is a hidden coupling
  between two static methods. Just write the file.

- **[Medium] `CLIError` has no error messages.** `CLIErrors.swift:11-18` is a bare `enum … : Error`.
  ArgumentParser prints these as something like
  `Error: The operation couldn't be completed. (mport.CLIError error 3.)`. Conform to
  `LocalizedError` and give each case an `errorDescription` — for a CLI, the error message *is* the
  user interface, and this is a ten-minute fix with an outsized payoff.

- **[Low] `outputSteamFailure` is missing its `r`** (`CLIErrors.swift:16`), `missingArgument` is
  never thrown, and "proivided" appears twice in `Export.swift` comments. Rename now while there are
  four call sites.

- **[Low] `CLIConfig.swift:41` — `return config;`** That semicolon is your TypeScript muscle memory
  waving hello.

## A note on Import.swift

You're writing it as I review, so this is a heads-up rather than a critique: it is currently
reproducing the patterns above before they're fixed. `var connectionURI: String = ""` at
`Import.swift:43` is the sentinel-string habit again, and all five parameters are positional
`@Argument`s.

One thing worth catching immediately: you define a perfectly good `CollisionResolution` enum at
`Import.swift:12`, then declare the argument as `var collisionResolution: String`
(`Import.swift:39`). Make the enum `ExpressibleByArgument` and use it as the property type —
ArgumentParser will then validate the input, reject bad values with a proper error, and list the
valid options in `--help`, all for one line of conformance. `OutputFormat` wants exactly the same
treatment.

Fix the patterns in `Export` first, then write `Import` against the fixed versions. Otherwise you're
writing the second copy of the same cleanup.

## Where to level up next

Four concepts, each one visible in this codebase, each with an exercise against your own code.

### 1. Optionals instead of sentinel values

You wrote `case pending = ""` (`OutputFormats.swift:12`), `var exportPath: String = ""`
(`Export.swift:16`), and `var connectionURI: String = ""` (`Export.swift:32`). All three mean "not
set yet" — which is precisely what `Optional` is for. The tell is `OutputFormats.swift`'s knock-on
effect: because `.pending` is a real case, it appears in `allCases`, so `Export.swift:67` has to
filter it back out with `.filter { $0 != "" }`. A sentinel value is a hole you then spend code
patching around, and it's `Codable`, so `""` can be written to disk as a "format."

**Exercise:** Delete `case pending` entirely and change `exportFormat` to `OutputFormat?`. The
compiler will produce a list of every place that assumed a non-optional. Work through them — you'll
find the `allCases` filter deletes itself, and the "did the user give us a format?" question becomes
`if let` instead of a string comparison. That's the whole lesson: `Optional` makes "absent" a state
the compiler tracks for you.

### 2. Exhaustive switches over your own types

`default:` in a `switch` over an enum you own throws away Swift's best feature. Right now you have
one at `Export.swift:152` and an `if/else if/else` chain at `Export.swift:172-207` doing the same
job.

**Exercise:** Remove both `default` branches and convert the chain to a `switch`. Then add
`case csv` to `OutputFormat` and *don't* implement it. Count the compile errors. Every one of those
is a bug that would otherwise have shipped and surfaced at runtime. Then delete the case again.

### 3. Errors are a user interface

For a CLI, the error message is the entire UX. `CLIError` currently produces
`The operation couldn't be completed. (mport.CLIError error 3.)`, and `Export.swift:105` makes it
worse by catching MongoKitten's real error and replacing it with `CLIError.connectionFailed` —
discarding whether it was auth, DNS, or TLS.

**Exercise:** Conform `CLIError` to `LocalizedError` and write an `errorDescription` for each case,
as a sentence you'd want to read at 2am. Add an associated value to `connectionFailed`
(`case connectionFailed(underlying: Error)`) and include the real reason. Then trigger each error
deliberately and read what your tool prints.

### 4. `let` at point of use

The block of `var`s at `Export.swift:32-37` is a habit from languages where declarations hoist.
Swift wants the opposite: declare where you know the value, prefer `let`, and let the compiler prove
each is assigned exactly once. (The `return config;` at `CLIConfig.swift:41` is the same muscle
memory in miniature.)

**Exercise:** Delete all six declarations at the top of `run()` and fix the resulting errors by
declaring each at its first real assignment. Count how many become `let`. Then notice that the ones
that genuinely *must* stay `var` are exactly the ones tangled in the multi-step resolution logic —
that's not a coincidence, it's the function telling you where it wants to be split.
